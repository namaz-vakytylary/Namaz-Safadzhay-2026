# Безопасность подписи — тестовая конфигурация

## Что меняется

Ветка `test/1.2-test3-security` продолжает проверенный test3.1. Код Android-приложения,
package `ru.namaz.safadzhay.test`, versionCode 36, versionName `1.2-test3.1`,
расписания и сертификат остаются прежними. Меняется способ передачи подписи в сборку.

- В текущем дереве нет keystore; пароли не записаны в Gradle.
- Ключ и три параметра подписи передаются через GitHub Actions Secrets.
- Секреты доступны только шагу сборки подписанного APK, после тестов и lint.
- Ключ создаётся во временном каталоге runner с правами 0600, каталог — 0700.
  Существующий файл или symlink не перезаписывается. При ошибке значения не печатаются.
- Временный ключ удаляется шагом `always()`; в артефакты попадают только APK и отчёты.
- GITHUB_TOKEN ограничен `contents: read`; checkout не сохраняет credentials.
- Без параметров подписи выпуск APK блокируется, без подстановки debug-ключа.
- Существующая проверка сравнивает сертификат APK с `verification/release-certificate.sha256`.
- Preflight запрещает отслеживаемые `.jks`/`.keystore` и пароли-литералы в Gradle.

## Что это не устраняет

Ранее опубликованный production signing key следует считать скомпрометированным.
Сохранение той же пары ключей в Secrets, смена пароля keystore, удаление текущего файла
или закрытие репозитория не отзывают уже полученные посторонними копии ключа.
История Git и прежние ветки, включая main, в этой задаче не переписываются.

## План окончательного устранения утечки

1. Сохранить резервную копию действующего ключа в защищённом хранилище владельца;
   зафиксировать публичный отпечаток опубликованных APK и список каналов распространения.
2. Проверить способы восстановления GitHub, двухфакторную защиту, активные сессии,
   участников обоих репозиториев, deploy keys и приложения с правом записи.
   Незнакомые доступы сначала показать владельцу; не удалять автоматически.
3. Уточнить у RuStore поддерживаемую процедуру смены ключа для уже опубликованного
   приложения, включая прямые APK-установки и поддерживаемые версии Android.
   Если используется Play App Signing, отдельно установить, раскрыт upload key
   или app signing key: процедуры и последствия различаются.
4. Подготовить конкретный план миграции и тест обновления поверх реального production
   APK с сохранением данных. Только после отдельного согласования менять production
   certificate, создавать новый production key или публиковать обновление.
5. Отдельно согласовать удаление секрета из остальных текущих веток и истории Git,
   старых исходных архивов/артефактов и возможных копий. Очистка истории требует
   согласованных действий с существующими клонами и не является отзывом ключа.

Для новой независимой тестовой линии можно отдельно согласовать тестовый сертификат.
Смена сертификата нынешнего test-приложения может нарушить обновление поверх test3/test3.1;
автоматически этого не делаем.

## Расписания

HTTPS, фиксированный источник, запрет редиректов, SHA-256, ограничения размера,
валидация JSON и атомарная запись сохранены. Контрольная сумма из manifest не защищает
от компрометации самого репозитория расписаний. Возможное отдельное усиление — подпись
manifest независимым закрытым ключом, который не хранится в репозитории/Pages, и проверка
встроенным открытым ключом в приложении. Это требует согласованного формата публикации,
резервирования ключа и перехода со старых APK; в этот перенос signing secrets не включено.
Доступ к расписаниям и их реальные значения не меняются.
