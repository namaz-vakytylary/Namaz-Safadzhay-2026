# Подготовка подписанного манифеста (не активирована)

Клиентский модуль `SignedManifestVerifier` не вызывается действующим обновлением.
Доверенных производственных ключей и нового серверного адреса в нём нет.
Текущая загрузка совместима с manifest schemaVersion=1 и пользователями 1.3.
SHA-256 и HTTPS не заменяют цифровую подпись издателя.

## Подготовленный протокол

Кандидат конверта: schemaVersion=2, keyId, payload, signature.
Payload — канонический Base64 точных UTF-8 байтов JSON с положительным `sequence`.
Signature — канонический Base64 64 байтов Ed25519. Подписывается
`UTF8("Namaz Vakytylary schedules manifest v2\0") || payload`.
Проверка подписи предшествует интерпретации payload. Повторная сериализация JSON
для проверки не используется. Неизвестный keyId, изменённые данные, некорректный
JSON, неверная подпись, неподдерживаемая схема и sequence ниже минимума отклоняются.

Использован Tink Android 1.23.0: приложение не регистрирует глобальный security
provider и не использует разрешающий fallback. Тесты RFC 8032, искажения,
неизвестного ключа и последовательности выполняются с Robolectric API 23/35.
Это JVM-проверки; обязательна дополнительная проверка на настоящем Android 6.
Официальная документация: https://developers.google.com/tink/setup/java

## Отдельное согласование перед включением

1. Утвердить протокол и источник нового подписанного файла рядом с v1.
   Старый manifest.json и действующие данные для 1.3 оставить доступными.
2. Владелец готовит закрытый ключ вне APK/публичного репозитория и определяет
   процедуру подписания. В APK закрепляются только публичные ключи и keyId.
   Тестовые эфемерные ключи не являются доверенными ключами приложения.
3. Выпустить клиент с подписанным начальным снимком/минимальным sequence.
   После перехода клиент не принимает неподписанные сетевые обновления.
   Старый проверенный локальный v1-кеш остаётся доступен офлайн до появления
   подходящего подписанного снимка, с сохранённым происхождением данных.
4. Подписанный кеш, sequence и его digest сохранять одной транзакцией/журналом.
   При том же sequence требовать тот же digest. Поддерживать отдельный сохранённый
   минимум для восстановления после повреждения основного файла.
5. Ошибки подписи/сети не удаляют последнюю проверенную копию. Восстановление —
   той же подписанной ревизией с тем же digest либо более новой подписанной
   ревизией. Ошибка не должна включать fallback к неподписанному серверу.
6. Ротация ключа — заранее утверждённым набором доверенных ключей в APK либо
   подписанным действующим ключом переходом с явной эпохой доверия.

Ограничения: удаление данных приложения/переустановка уничтожает локальную
историю; поэтому нужен минимальный sequence, закреплённый в APK. Подпись сама по
себе не обнаруживает бесконечную выдачу одной старой допустимой версии (freeze).
Нужна согласованная политика свежести без отключения офлайн-расписаний.
Серверный формат, ключи и обязательная проверка в этой работе не меняются.
